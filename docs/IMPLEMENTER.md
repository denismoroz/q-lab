# Агент-реализатор: карточка → код → исход (2026-10-03, дополнено 2026-10-27)

Владелец, 2026-10-03: «делай все 3 одну за одной» — вторая из трёх. Раньше каждая стратегия
писалась руками по карточке. Реализатор (`src/qlab/agents/implementer.py`, модель sonnet по
`docs/PLAN.md`) пишет два файла и больше ничего:

- `src/qlab/strategies/agent/<модуль>.py` — класс стратегии (`qlab.harness.strategy`);
- `specs/agent/<идея>.yaml` — её спек, у каждого числа указан источник (`docs/SOURCES.md`).

Читать репозиторий он может (Read, Glob, Grep), писать — только эти два файла, запускать ничего
не может (Bash отключён). Дальше работает код, а не агент:

1. изменены только два разрешённых файла — всё прочее откатывается, попытка не засчитана;
2. спек загружается, у каждого числа проверяемый источник;
3. модуль импортируется и выглядит как стратегия;
4. агент-проверяющий сверяет код с карточкой (`docs/REVIEWER.md`), пробел с доказательством
   останавливает прогон;
5. стенд: проверка на подглядывание, случайные книги, правила.

Если карточку нельзя выразить на данных стенда, агент так и отвечает («NOT EXPRESSIBLE»), и это
ответ, а не сбой. Вручную — `qlab implement cards/<карточка>.yaml`.

Задняя половина — это реализатор и всё, что идёт после него. Карточка без этих полей идёт как
раньше.

### Что делает агент: блок, а не разовая поделка

Для карточки с `new_block` агент пишет **переиспользуемый блок**: один модуль с именем блока
(`src/qlab/strategies/agent/<имя блока>.py`), в котором **каждый параметр сетки читается из
`params`** (точка в пути — вложенный словарь), и ни одно из чисел не зашито в класс. В спеке
стоят числа **первого варианта** сетки. Сетку и обёртку перенастройки он не пишет — это дело кода.
Другой спек потом называет этот модуль в `code_ref` с другими числами, и тот же класс работает.

Если модуль с таким именем уже есть (его написала более ранняя карточка), агент его читает и
**не меняет**: пишет только спек. Любая правка существующего модуля откатывается и проваливает
попытку. Уже написанные блоки перечислены в задании агента (из `night/agent_blocks.yaml`), чтобы
не писать второй такой же.

К пяти проверкам добавляется шестая, кодом (`card_problems`):

- в спеке есть каждый параметр сетки и стоит первый вариант карточки;
- код модуля вообще называет каждый параметр сетки по имени (страховка от числа, зашитого в
  класс: это не доказательство, но параметр, которого код ни разу не называет, из `params`
  прочитать нельзя);
- данные спека — те, что сказаны в карточке (площадка, шаг свечей).

Блок записывается в `night/agent_blocks.yaml` **кодом** и только после всех проверок и проверяющего
(`qlab.agent_blocks`): что это за блок, что значит каждый параметр, какие карточки и спеки его
используют. Записывать в реестр блоков сам агент не может.

> Реестр блоков составных стратегий (`qlab.strategies.blocks`) — это словарь функций в коде, и
> добавить туда блок значит править код. Поэтому написанный агентом блок — целый класс
> стратегии, а не функция сигнала; он доступен всем, кто назовёт его в `code_ref`.

### Что делает ночь после проверок (код, токенов не тратит)

Порядок фиксирован, каждый шаг — прогон, пишущий свои испытания (дефляция считает все):

1. **написанная версия** — спек как есть, на стенде, случайные книги как настроено;
2. **версия с выбором кода** — тот же спек, но число из сетки карточки раз в месяц выбирает код,
   **только по прошлому**: окно растущее, мерка — Шарп после издержек, данные Binance с
   2019-09-08 (или с `honest_from` карточки). Это тот же «двойник» (`docs/RETUNE.md`), только
   варианты задаёт карточка, а не пара «база + эксперимент» или общие списки;
3. **база** — `baseline_spec`, прогнанная на **тех же данных, с теми же издержками и с той же
   судимой частью**, что и версия с выбором кода, чтобы в отчёте сравнивались равные. Если версии
   с выбором кода сделать нельзя, база встаёт на данные написанной версии, и отчёт это говорит;
4. **второй этап** на Hyperliquid (`docs/TWO_STAGE.md`; тот же вызов, что у генератора, не замер)
   — для каждой прошедшей первый этап версии: написанной (если её данные с Binance — иначе она
   уже на данных площадки исполнения, и отчёт так и пишет) и версии с выбором кода.

Ночной срок (`--stop-at`) проверяется перед каждым шагом. Недоделанное лежит в журнале
`data/implement/ledger.json`: следующая ночь **продолжает** с того же места, агента заново не
зовёт и токенов не тратит, готовые прогоны не повторяются. Шаг, упавший с ошибкой, пробуется ещё
раз на следующую ночь (всего два раза).

Тяжёлые данные не качаются: правило двойников (`night/twins.yaml`, `docs/NIGHT.md`) действует на
каждый шаг. Часовые свечи всех контрактов Binance не берутся за ночь — шаг помечен «слишком
тяжёлые» с причиной, а вручную их можно прогнать (`qlab twins run --allow-heavy`).

### Как строится версия с выбором кода

Общие части с двойниками (`src/qlab/twin.py`), а не копия:

- `card_grid` собирает сетку из полей карточки (`params` — списки, `candidates` — именованные
  наборы), проверяет, что числа первого варианта стоят в спеке, что вариантов не больше
  `max_candidates` (`night/own_numbers.yaml`), и цитирует карточку: каждое число сетки буквально
  стоит в её файле;
- `causal_twin(..., grid=...)` делает остальное так же, как для любого двойника: обёртка
  `Retune`, разгон по самому длинному окну параметров, первый выбор после целого периода, данные
  Binance, `selects_causally`;
- `honest_from` карточки: если монеты названы **списком**, версия судится только со дня, когда
  список был известен (`judged_from` = `instruments_chosen_at`), а история до него — разгон для
  выбора; без даты список датируется днём написания спека, и судить нечего (правило
  `docs/RETUNE.md`, «Двойник часовой идеи»). Если списка нет, данные начинаются не раньше этой
  даты;
- `execution_venue` — площадка из карточки, если её данные на Binance лишь заменитель.

База строится `same_panel_spec`: данные, издержки и судимая часть версии с выбором кода, числа
самой базы не тронуты. Файлы: версия с выбором кода — `specs/agent/<идея>-causal.yaml` (готовый
файл никогда не переписывается), база — `data/implement/baselines/<идея>-base.yaml`.

### Границы

- Пробел между карточкой и кодом, найденный проверяющим с доказательством, оставляет только
  первый шаг: стенд ответит «проверить было нечем», а прогоны версии о другой стратегии не нужны.
  Блок в реестр не записывается; карточка ждёт владельца.
- Две неудачные попытки агента — и карточка ждёт владельца (как запросы программиста,
  `docs/PROGRAMMER.md`); готовая и «выразить нельзя» карточки не берутся заново.
- Вердикт не выносит никто, кроме стенда. Сетка — выбор автора карточки: её честность настолько
  же, насколько честна сама сетка (так сказано и в источниках версии с выбором кода).

### Отчёт

Раздел «Реализация карточек агентом» утреннего отчёта по каждой карточке показывает: слова идеи,
написанный блок (правило, параметры, новый он или повторное использование), короткое пояснение
версии с выбором кода и таблицу

| версия | данные | в год | Шарп | просадка | без 1% лучших дней | исход |

по трём строкам (база, написанная, с выбором кода), под ней «по годам» для каждой версии
(`docs/YEARS.md`), строки второго этапа и, где что-то не прогнано, причина простыми словами.
Строка «написанная» считается на своих данных, база и версия с выбором кода — на общих; отчёт
говорит об этом. Те же факты — на странице «Агенты» консоли.

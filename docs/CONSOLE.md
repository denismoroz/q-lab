# Консоль: как она работает и как её обновлять (2026-11-03)

Владелец, 2026-11-03: «похоже сломалась панель». Причина: консоль на порту 5890 отдавала **рабочую
папку** репозитория (так работает dev-сервер `npm run dev`): полуготовая правка файла в `web/src/` или
ветка, на которую переключились на час, тут же показывались на странице владельца и ломали её. Теперь
консоль отдаёт **собранную страницу** `web/dist/`; рабочая папка и ветки её не касаются, пока страницу
не соберут заново.

## Слова

**Консоль** — страница владельца, `http://localhost:5890`. **API** — программа на порту 8890, которая
читает реестр и отдаёт данные консоли (`ops/api.sh`); код API подхватывается отдельно, перезапуском.
**Сборка** — превращение исходников страницы (`web/src/`) в готовые файлы (`web/dist/`).
**launchd** — служба macOS, которая запускает консоль и API при входе и поднимает их, если упали.
**main** — главная ветка репозитория; в неё попадает только то, что владелец или его помощник приняли.

## Как это работает

- launchd держит службу `com.qlab.console` (`ops/com.qlab.console.plist`), она запускает
  `ops/console.sh`, а тот — `vite preview`: маленький сервер, который отдаёт файлы из `web/dist/` и
  пересылает всё, что начинается с `/api`, на API (порт 8890), как и раньше dev-сервер.
- `web/dist/` лежит в репозитории, но **не** в git (`.gitignore`), поэтому переключение веток его не
  меняет. Меняет его только `ops/console-build.sh`.
- Если `web/dist/` нет (первый запуск на новой машине), `ops/console.sh` один раз собирает страницу из
  `main` сам и не уходит в цикл перезапусков.
- API по-прежнему отдельная служба (`com.qlab.api`): новый код API подхватывается
  `launchctl kickstart -k gui/$(id -u)/com.qlab.api`. После запуска API сам собирает в фоне то, что
  регистру нужно для страницы «Реестр» (надписи скамейки, короткие названия); первая загрузка
  страницы не ждёт.

## Как обновить страницу

**После каждого слияния в `main`, которое трогает `web/`**, один раз:

```bash
ops/console-build.sh
```

Скрипт:

1. выгружает папку `web/` из **закоммиченного** `main` (`git archive`), а не из рабочей папки, так что
   полуготовая правка на страницу не попадёт;
2. собирает её во временной папке (`npm ci`, `vite build`);
3. только после успешной сборки подменяет `web/dist/` (если сборка упала, страница владельца не
   меняется);
4. перезапускает службу консоли (`launchctl kickstart -k gui/$(id -u)/com.qlab.console`); если служба
   не загружена, говорит об этом и ничего не ломает.

Ночному конвейеру сборка **не нужна**: ночь страницу не читает. Слияния, которые трогают только
Python-код API, перезапуска консоли не требуют, достаточно `kickstart` службы API.

`BRANCH=<ветка> ops/console-build.sh` соберёт страницу из другой закоммиченной ветки (посмотреть
чужую работу целиком); `ops/console-build.sh --no-restart` только соберёт, не трогая службу.

## Как установить (один раз, после слияния этой правки)

Сама служба не менялась (тот же `ops/console.sh`, тот же путь), поэтому установленную копию
`~/Library/LaunchAgents/com.qlab.console.plist` заменять не нужно. Достаточно:

```bash
ops/console-build.sh        # соберёт web/dist из main и перезапустит консоль
```

## Вернуться к dev-серверу (для разработки)

Dev-сервер удобен, когда правишь `web/src/` и хочешь видеть правки сразу. Он занимает тот же порт, поэтому
сначала останавливают службу:

```bash
launchctl bootout gui/$(id -u)/com.qlab.console     # остановить консоль владельца
cd web && npm run dev                               # http://localhost:5890, правки видны сразу
```

Закончив:

```bash
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.qlab.console.plist
```

Пока dev-сервер запущен, страница владельца — рабочая папка, как раньше; не оставляйте его надолго.
Чтобы посмотреть правку **рядом** с работающей консолью, не останавливая её, поднимите вторую консоль на
другом порту и, при желании, с другим API:

```bash
cd web && npm run build && QLAB_API=http://127.0.0.1:8891 npx vite preview --port 5991
```

(`QLAB_API` — куда пересылать `/api`; по умолчанию `http://127.0.0.1:8890`.)

## Страница «Реестр» (2026-11-03)

Три просьбы владельца в один день, все они читаются из реестра и ничего не решают:

1. **«Скамейка» разведена на три надписи** (`src/qlab/bench_label.py`; «да, разведи на три надписи»).
   Статус в реестре по-прежнему `bench`, а надпись выводит код по последним прогонам каждой площадки
   (`docs/LADDER.md`, раздел «Скамейка — три надписи»). Фильтр статусов предлагает их отдельными
   кнопками, выбор лежит в адресе: `?status=bench-too-early,bench-passed-no-execution`; старая ссылка
   `?status=bench` включает все четыре.
2. **Фильтр по семейству** («почему я не видел этих стратегий в фильтре?» → «добавь фильтр по
   семейству»). Семейство определяет корень цепочки родителей идеи (`qlab.registry.strategies`):
   Bv2, Bv3, Тренд, FRAB, FRAB на споте, XSMOM, механизмы генератора, прочее. Он сочетается с фильтром
   статусов (`?family=bv2&status=bench-too-early`), цифра на кнопке — сколько идей останется, если её
   нажать при остальных выбранных фильтрах. Рядом с номером идеи стоит её короткое простое название
   (то, с которого начинается страница идеи).
3. **«Сменилось»**: метка у идеи, статус которой менялся за последние 24 часа (из журнала переходов
   `stage_transition`), на подсказке — «было → стало»; цепочка шагов за ночь читается одним шагом, а
   идея, вернувшаяся туда, откуда вышла, метки не получает. Есть фильтр «изменились за сутки»
   (`?changed=1`).

## Одно место для идеи, одно слово для ступени (2026-11-04)

Владелец, 2026-11-04: «у нас есть карточки кандидатов и реестр - и там тоже есть статус кандидат -
очень похоже на дупликацию. нужно убрать поидее что-то». Одна и та же идея показывалась на двух
страницах под одним словом. Теперь путь идеи такой, и у каждой ступени своё место:

`ideas/inbox.yaml` (сырая идея) → карточка в `cards/` → `qlab import-cards` вносит идею в реестр →
реализация → прогоны.

1. **Реестр — единственное место для идей, которые уже есть.** Карточка (пересказ простыми словами,
   источники, шесть частей, проверяемость, связь с известным) теперь раздел страницы идеи —
   блок «Карточка» сразу под «Что делает стратегия», свёрнут. Отдельной страницы карточки нет.
2. **«Карточки кандидатов» стала страницей «Входящие»** (`/inbox`, `src/qlab/api/inbox.py`). Она
   показывает только то, чего ещё нет в реестре, и ступень каждой идеи (код читает её из записи
   входящих, сам ничего не решает):
   - «ждёт карточника» — запись `new`, карточник за неё ещё не брался;
   - «карточка пишется / не принята (попытка N)» — карточник пробовал, код не принял черновик;
     причины видны под идеей;
   - «вопрос владельцу» — с самим вопросом;
   - «повтор уже сделанного» — с тем, что она повторяет;
   - «карточка готова, ждёт реализации» — пока идея не внесена в реестр (карточка открывается
     тут же, `/inbox/<идея>`; сюда попадает и карточка без записи во входящих);
   - «уже в реестре» — ссылка на страницу идеи, карточка второй раз не показывается;
   - «закрыта владельцем».
3. **Старые ссылки `/cards/<идея>`** ведут на страницу идеи, если идея в реестре (`GET /api/cards/<идея>`
   отдаёт `page`), иначе — на карточку во входящих; `/cards` ведёт на `/inbox`.
4. **Слово «кандидат».** Статус в реестре по-прежнему хранится как `candidate`, а читается как
   **«ещё не прогонялась»**: в реестре, фильтрах, на странице идеи, в воронке и в утреннем отчёте
   (`src/qlab/status_words.py`, `web/src/labels.js`). Шумовые книги (8 штук, тоже `candidate`) — не
   идеи: их нет ни в одном счёте идей, они лежат отдельным свёрнутым разделом реестра «Шумовые книги
   (инструмент)».
5. **Воронка согласована**: блок «Путь идеи» считает каждую идею один раз — входящие (без карточки) →
   карточка готова, в реестр не внесена → в реестре, ещё не прогонялась → прогонялась
   (`idea_path` в `GET /api/funnel`); числа те же, что на страницах «Входящие» и «Реестр».

## Страница «Стандарт» (2026-11-04)

Владелец, 2026-11-04: «гдето они есть гдето нет - разберись пожалуйста с это кашей. составь список
фич который должен быть у стратегии и прогони все стратегии под одну гребенку».

- В меню — «Стандарт» (`/standard`): таблица «идея × четырнадцать пунктов страницы стратегии»,
  зелёное — есть, красное — не хватает, серое — не нужно; причина — в подсказке над ячейкой,
  название пункта — над номером столбца. Вверху фильтр по семейству (как в реестре, лежит в адресе
  `?family=`), внизу строка итогов и перечень того, чего не хватает чаще всего.
- На странице каждой идеи сразу под простым описанием — панель «Что есть на странице: N из 14» с
  перечнем недостающего; полный список раскрывается.
- Список пунктов, правила «есть / нет / не нужно» и команда `qlab standard` — в
  `docs/IDEA_STANDARD.md`, раздел «Как проверка работает и где страница «Стандарт»».

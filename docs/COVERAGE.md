# Книга, монеты которой появились в разное время: два способа посчитать (2026-11-05)

Владелец, 2026-11-05: «да, сделай замер обоими способами». Какой способ честнее — решает владелец,
когда увидит цифры; пока это только замер, который **ничего не решает** (его правило: «сначала замер,
потом правило» — решающим замер становится по статистике).

## О чём вопрос

Книга из нескольких монет (Bv2: BTC, ETH, SOL, AVAX; у каждой монеты ноги — спот и контракт)
листингом начиналась в разные годы. Стенд сегодня судит такую книгу **только с того дня, когда у
всех её ног уже есть история** (правило «полной книги», `docs/REGIMES.md`, `complete_book_window`
в `src/qlab/pipeline/evaluate.py`). Плюс сама спека может просить данные не с самого начала.
Пример — `bv2-binance`: судится с 2023-04-28, и последняя треть окна (правила 2026-11-04.2)
начинается 2025-09-01. Тот же боевой код, запущенный с 2019 года, где каждая монета входит в
книгу, когда у неё появились обе ноги, даёт последнюю треть с 2024-06 и совсем другое число.

## Два способа

1. **Как есть** — то, что делает стенд: окно данных спеки, отсечка «полной книги», последняя треть
   этого окна.
2. **Монеты входят по мере появления** — тот же код и те же параметры на окне от первого дня, когда
   есть данные хоть у одной ноги книги. Монета входит, когда есть обе её ноги; пока её нет, её доля
   денег лежит в стороне наличными (боевой Bv2 так и делает: книга монеты открывается на первом
   часе, когда обе ноги торгуются, а деньги её места до этого ждут; стратегия весов держит у
   ненайденной монеты нулевой вес). Отсечка 2/3 — 1/3 правил 2026-11-04.2 применяется к более
   длинному окну; те же издержки; проценты — на деньгах стратегии (`cap_*`,
   `docs/CAPITAL_BASE.md`).

**Монета не раньше дня, когда её можно было выбрать.** Список, написанный вручную, мог знать,
какие монеты вырастут (`night/knowable_coins.yaml`, `src/qlab/knowable_coins.py`, `docs/ONE_CHECK.md`).
Поэтому во втором способе монета не входит раньше первого дня, когда по данным самой биржи она была
«очевидным выбором» (на бирже не меньше 30 дней и в первой десятке по обороту за предыдущие 30
дней). Монета, которая очевидным выбором не была ни в один день, входит со дня появления ног и
помечена. Для книги, чьи монеты выбирает сама стратегия (`params.universe`), такое ограничение не
нужно.

## Что показано по каждому способу

Окно; день, с которого начинается последняя треть; доход в год за последнюю треть и худшее падение
на деньгах стратегии; отличим ли заработок от нуля (p по перемешиванию дней, `docs/NOISE_BAR.md`);
доля последней трети, в которой книга была неполной. Шум (место среди случайных книг) здесь не
считается: 200 книг на каждое чтение — дорого; место на шуме остаётся на запуске стенда.

Хранится по идее в `data/coverage_compare/<идея>.json` (путь можно сменить переменной
`QLAB_COVERAGE_COMPARE`); на странице идеи — блок «Два способа считать книгу, монеты которой
появились в разное время». Считает команда:

    uv run qlab coverage-compare IDEA [IDEA ...]
    uv run qlab coverage-compare --all    # все открытые идеи, чьё окно режет правило полной книги

## Что важно знать

- Спека с записью «судить только с такого-то дня» (`judged_from`, например список монет, записанный
  2025-06-01 у причинных идей) в обоих способах остаётся на этом дне: окна совпадают, и блок это
  говорит.
- Боевая Hyperliquid отдаёт часовую историю только за последние месяцы, поэтому на ней длинное окно
  всего на 1–2 месяца длиннее.
- Первый способ воспроизводит последний запуск стенда один в один (доход, падение, p и длина
  последней трети совпали у всех идей).

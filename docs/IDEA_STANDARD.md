# Стандарт страницы стратегии: одна гребёнка для всех

Владелец, 2026-11-04:

- «опять на всех стратегиях разные данные. я просил чтобы была информация - график о том как работает
  стратегия на по периоду доступному по данным … таких графиков нет. гдето они есть гдето нет -
  разберись пожалуйста с это кашей. составь список фич который должен быть у стратегии п прогони все
  стратегии под одру гребенку»;
- «все стратегии должны проходить проверку вперед по 2/3 и 1/3 правилу».

## Откуда была каша (что нашли)

1. **График рисовался только у прошедших.** Панель «Как отработала проверка вперёд» показывалась
   только идее с исходом «прошла все правила, ждёт решения владельца». У
   `bv2-fast-release-by-own-trend` исход «прошла, но нет площадки исполнения» — и графика нет, хотя
   прогон есть.
2. **График показывал только проверку вперёд**, а не весь период данных.
3. **Ряд сохранялся только у живых исходов**: у отказа графика не было, и не видно, почему отказ.
4. **Проверка вперёд резалась по дню фиксации чисел, а не по данным.** Правило 1/3 было, но мерило
   длину проверки от дня, когда кто-то записал числа. Если числа записал человек 3 октября, проверка
   вперёд — 27 дней, и идея неделями «ждёт новых данных». У одной идеи проверка вперёд — два года, у
   соседней — месяц. Это и есть «на всех стратегиях разные данные».
5. **Список монет мог сузить агент молча.** Bv3 гоняли на BTC и ETH, хотя владелец этого не просил:
   исследователь взял за основу свой старый опыт на двух монетах.

## Правило 2/3 и 1/3 (одно для всех)

- **Период** — все данные площадки, на которых стратегия может работать (по каждой площадке свой:
  Binance с 2019 года, Hyperliquid с начала своих данных), за вычетом разогрева (дней, нужных
  стратегии, чтобы посчитать свой первый сигнал) и с учётом «очевидного списка монет»
  (`docs/ONE_CHECK.md`). Короче — только с названной причиной.
- **Первые 2/3 периода — подбор.** Если идея объявила варианты чисел (`choice`), код выбирает лучший
  набор по этим двум третям (доход после издержек на единицу колебаний) — один раз.
- **Последняя 1/3 — проверка вперёд.** Числа на ней не меняются. Решающие правила читают её.
- Так длина проверки вперёд у всех — треть их данных, и «ждёт новых данных» по длине больше не бывает.
- **День, когда числа записал человек**, остаётся замером, а не правилом: если числа выбраны, когда
  последняя треть уже была видна, страница пишет «числа выбраны, когда эта треть уже была известна —
  проверка вперёд не чистая». Решающим это делает только владелец (`qlab-measure-before-rule`).
- Книги на бумаге и в деньгах проверяются так же на стенде; их настоящая проверка — торговля, она
  идёт рядом, как раньше.

## Что должно быть у каждой стратегии

Каждый пункт на странице есть, или вместо него написано, почему нет. Список проверяет код
(`qlab.idea_standard`), а не человек.

1. **Простыми словами** — что стратегия делает, на чём должна зарабатывать, в чём риск.
2. **Карточка** — откуда идея и кто её предложил.
3. **Итог и почему** — статус и одна фраза причины.
4. **Лестница оценки** — семь ступеней, у каждой «пройдена / не пройдена / пропущена, потому что».
5. **График денег стратегии за весь период данных** — по каждой площадке; первые 2/3 (подбор) и
   последняя треть (проверка вперёд) различимы; серая линия «просто держать те же монеты».
   Для любого исхода, включая отказ.
6. **По годам** — доход и худшее падение каждого года.
7. **Главные числа на деньгах стратегии** — доход в год, худшее падение, отношение дохода к
   колебаниям (Шарп), доход без 1% лучших дней — отдельно за подбор и за проверку вперёд.
8. **Планка шума** — лучше ли случайных книг, и хватает ли данных, чтобы это сказать.
9. **Нужные деньги** — сколько нужно, чтобы поставить все ордера, и как работает на $1k / $3k / $10k.
   С правил `2026-11-04.2` ещё и решающая строка: книга «меньше позиций» на деньгах самой стратегии
   (`docs/MONEY_LADDER.md`, раздел 0); площадка, где она не измерена, — пробел с причиной.
10. **Обе площадки** — Binance и Hyperliquid, у каждой свой итог или причина, почему его нет.
11. **Данные** — с какого по какой день, и почему не раньше.
12. **Монеты и кто их выбрал** — список и источник: правило кода, слово владельца или объявленный
    выбор. Сужение без источника — дефект.
13. **Издержки** — комиссии, проскальзывание, плата за удержание контракта.
14. **Проверка на двойника** — нет ли уже такой же идеи.

## Монеты: сужать молча нельзя

- Если в опыте монет меньше, чем у стратегии-родителя (по карточке или боевому спеку), у сужения
  должен быть источник: слово владельца (`sources["coins"]` с цитатой) или объявленный выбор
  (`choice`). Иначе опыт не запускается, и отказ пишется с причиной. Как это проверяется —
  `docs/COIN_SCOPE.md`.
- **Bv3**: монеты выбирает код — каждый день первые K монет по обороту за 30 дней на площадке; K —
  объявленный выбор из 2, 4, 6, его выбирает код на первых двух третях. Это проверит и догадку
  исследователя, что SOL и AVAX «дёргают страховку», вместо того чтобы принять её на веру.

## Как прогоняем всё под одну гребёнку

1. Новая версия правил с разрезом 2/3 и 1/3 — сделано: `rules/2026-11-04.1.yaml` (`docs/FIT_VS_FORWARD.md`).
2. Ряд денег за весь период хранится у каждого прогона, любого исхода.
3. Все неубранные идеи с прогоном перепрогоняются по новым правилам (расчёт, без агентов и токенов);
   у каждой страница проверяется по списку выше.
4. Страница «Стандарт» в консоли: идеи × пункты, где чего не хватает и почему.

## Как проверка работает и где страница «Стандарт» (2026-11-04)

Код — `src/qlab/idea_standard.py`. Он ничего не считает заново (ни прогонов, ни метрик) и ничего не
пишет: читает то, что страница идеи и так читает (записи реестра, лестницу оценки, сохранённые ряды
денег, файл спека, начало данных площадки в сыром кэше), и по каждому из четырнадцати пунктов
отвечает одним из трёх слов:

- **есть** — пункт на странице есть;
- **нет** — не хватает, рядом простыми словами написано, чего именно и почему («Hyperliquid: ряд
  денег ещё не построен — будет после пересчёта», «список монет сужен без источника: …», «период
  короче доступного: начинается с …, потому что …»);
- **не нужно** — этой идее не применимо, причина названа («ещё не прогонялась»; «прогона нет: идея
  закрыта до расчёта»). В «N из 14» такие пункты не считаются имеющимися.

Не проверяются убранные владельцем идеи (`retired`) и книги для калибровки шума. Второй этап идеи
(`<идея>-hl`) отдельной строкой не идёт: это вторая площадка той же идеи, и пункты 5, 9, 10, 11, 12
смотрят на обе площадки.

Как читается каждый пункт:

| № | «есть», если | «нет», если |
|---|---|---|
| 1 | у страницы есть простой текст (спек, карточка, семейство) | текста нет |
| 2 | есть карточка идеи, или её предка, или источник записан в самом спеке | ничего из этого |
| 3 | у идеи есть прогон с записанным исходом | прогон есть, а исход не записан (старые прогоны) |
| 4 | лестница из семи ступеней построена | не построена |
| 5 | у последнего прогона **каждого этапа** лежит ряд формата 2 (весь период) | ряда нет, или он только за проверку вперёд |
| 6 | годы есть и на деньгах стратегии | годов нет или они только на балансе книги |
| 7 | числа на деньгах стратегии, отдельно подбор и проверка вперёд, прогон по правилам 2/3 и 1/3 (2026-11-04.1 и новее) | иначе, с причиной |
| 8 | есть и «лучше ли случайных книг», и «хватает ли данных» | не хватает одного из двух |
| 9 | для каждой площадки с прогоном есть «нужно денег» и ряд на $1k / $3k / $10k | не измерено |
| 10 | у каждой площадки есть итог, или названа причина, почему версии там нет по природе идеи | «ещё не прогонялась», «стоит в очереди», сбой |
| 11 | начало данных — начало данных площадки, либо код знает причину (разогрев стратегии, день появления монеты, проверка «очевидного списка», причина в `sources["data.start"]`) | период короче доступного без причины, которую проверит код; день, который записал человек, причиной не считается |
| 12 | монеты выбирает правило кода, список очевидный по данным биржи, слово владельца, объявленный выбор, список боевой книги или источник идеи | «выбраны агентом без источника» (дефект) |
| 13 | в спеке есть комиссия и проскальзывание | нет |
| 14 | проверка «дубль по результатам» (`docs/DUPLICATES.md`) проводилась: двойника нет или назван | не проводилась |

Пункт 14 помнит, что проверка была: `data/duplicates/ledger.json` теперь хранит ещё и `checked`
(идея → прогон, на котором проверяли). Для идей, прогнанных до этого, проверку можно провести одной
командой: `qlab standard --mark-doubles` (пишет только этот журнал).

Где это видно:

- **страница идеи**: у самого верха панель «Что есть на странице: N из 14» — в ней только то, чего
  не хватает, с причинами; полный список раскрывается кнопкой (`GET /api/ideas/<id>`, поле
  `standard`);
- **страница «Стандарт»** в консоли (`/standard`, в меню): строка — идея, столбец — пункт, ячейка
  зелёная / красная / серая, причина в подсказке при наведении; внизу итоговая строка «нет на
  странице, идей» и список самого частого (`GET /api/standard`; ответ хранится минуту, `?fresh=true`
  считает заново); фильтр по семейству лежит в адресе (`?family=bv2,trend`);
- **`qlab standard`**: та же таблица текстом (`+` есть, `-` нет, `.` не нужно), под ней — по каждому
  пункту, у скольких идей его нет и чаще всего почему. `qlab standard --idea ID` — полный список
  одной идеи с причинами, `--family`, `--status` — отбор, `--json` — как отдаёт API;
- **утренний отчёт**: раздел «Стандарт страницы стратегии», одна строка — «стандарт страницы: у N
  идей не хватает пунктов, чаще всего — …».

Чтобы закрыть пункт, нужно не править проверку, а сделать недостающее: перестроить ряды
(`qlab forward-series rebuild --all`), перемерить идеи по новым правилам (`qlab restamp run --all`),
записать причину в спек, дописать карточку.

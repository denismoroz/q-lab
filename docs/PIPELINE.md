# Ночь по шагам: пайплайн (2026-10-31)

Владелец, 2026-10-31: «разбиваем весь процесс на шаги. в qlab я хочу видеть весь пайплайн по
шагам. не зависимые шаги должны выполняться по любому. если какой-то шаг — падает — это не
должно останавливать весь процесс. в qlab я хочу видеть дерево запуска плюс историю запусков
каждого шага. описание краткое каждого шага». И: «я хочу понять и видеть что так долго
отрабатывает — можно ли запараллелить шаги. сейчас это для меня какой-то чёрный ящик». И: нужны
«текущее состояние пайплайна — упал красный, прошёл зелёный», перезапуск шага, который «влияет
на все», кнопка «запустить весь пайплайн» с выключением шагов, «статистика и зависимости по
каждому шагу».

Две ночи подряд пропали из-за шага, которого никто не видел: 29 октября один пункт два часа
качал данные, 31 октября очередь закрытых идей и пересчёт старых результатов три с половиной
часа качали свечи, срок прошёл до того, как дошла очередь до агентов. Теперь ночь — это
таблица шагов, у каждого видно, что с ним случилось и сколько он шёл.

## Что есть

* **Таблица шагов** — `night/pipeline.yaml`. Один список на всю ночь: название, одна строка
  описания, вид (данные / код / агент), тратит ли токены и от чего зависит. Порядок в списке —
  порядок, в котором ночь идёт сейчас (по одному шагу), и он всегда допустим: родитель стоит
  выше ребёнка (это проверяется при чтении таблицы).
* **Журнал** — три таблицы реестра (`pipeline_run`, `pipeline_step_run`, `pipeline_item`):
  каждый запуск, каждый шаг запуска (состояние, начало, конец, длительность, число сделанных
  дел, токены, текст ошибки, кто заблокировал), каждое дело внутри шага (имя, длительность,
  исход). Пишется по ходу: строка шага появляется в момент старта, а не утром.
* **Запуск** — тот же `qlab night run`. Идёт по таблице; упавший шаг блокирует только тех, кто
  берёт его результат, остальные идут. Всё остальное по-старому: те же этапы, продолжение с
  места остановки по отметкам «сделано», утренний отчёт, срок `QLAB_STOP_AT` (по умолчанию его
  нет).
* **Страница «Пайплайн»** в консоли: дерево шагов, цвета, описание, зависимости, статистика,
  история, две кнопки.

**Фоновая закачка не шаг.** Поток, который заранее качает данные списка наблюдения, пока
считается предыдущее (`qlab.prefetch`, `docs/NIGHT_SPEED.md`), запускается вместе с запуском и
останавливается перед лестницей оценки; в таблице шагов его нет. Что он сделал, лежит в
`prefetch` состояния ночи.

## Шаги и связи

Связь у шага — «зависит от». Видов четыре; **блокирует только первый**.

| вид | смысл | если родитель упал |
|---|---|---|
| данные | шаг берёт то, что родитель записал этой ночью; без этого он неверен | шаг **заблокирован** |
| свежесть | шаг читает то, что пишет родитель, но вчерашний ответ тоже верен; ждёт, чтобы прочитать свежее | идёт |
| не вместе | оба пишут испытания одних и тех же идей; одновременно одну идею посчитали бы дважды, и дефляция учла бы оба раза | идёт |
| порядок трат | только очерёдность расхода токенов (CLAUDE.md: урезание идёт с конца); данные не передаются | идёт |

Выключенный владельцем шаг блокирует зависящих «по данным» только если сегодня он ещё не
выполнялся. Выполнен утром — вечером его можно выключить, а зависящие от него пойдут.

| шаг | вид | токены | зависит от (и почему) |
|---|---|---|---|
| `detectors` Определители режима | данные | нет | — |
| `recheck` Список наблюдения | код | нет | определители (**данные**: стратегии списка читают их файлы) |
| `waiting` Ждущие идеи | код | нет | определители (**данные**: те же файлы) |
| `twins` Двойники | код | нет | список и ждущие идеи (свежесть: кому нужен двойник, видно по свежим исходам) |
| `restamp` Пересчёт старых | код | нет | список, ждущие, двойники (не вместе: идею нельзя считать дважды за ночь) |
| `venue_gap` Почему площадки расходятся | код | нет | пересчёт (свежесть) |
| `anomalies` Аномалии, проверка кодом | код | нет | пересчёт (свежесть) |
| `anomalies-investigate` Аномалии, разбор агентом | агент | да | проверка кодом (**данные**: разбирает те прогоны, где сработал признак) |
| `overlays` Надстройки | код | нет | проверка на аномалии (**данные**: базу выбирают только из проверенных чистых) |

| `allocation` Распределение капитала | код | нет | угасание (**данные**), сверка бумаги (свежесть) |
| `assess` Второе мнение | агент | да | список (**данные**: оценивает записанные им исходы), сверка (свежесть) |
| `programmer` Программист | агент | да | второе мнение (порядок трат) |
| `director` Руководитель | агент | да | программист (порядок трат) |
| `research` Исследователь | агент | да | руководитель (порядок трат) |
| `twins-research` Двойники экспериментов | код | нет | исследователь (**данные**: его эксперименты), двойники (не вместе) |
| `implement` Реализация карточек | агент | да | исследователь (порядок трат) |
| `search` Поиск | агент | да | реализация (порядок трат: поиск нового урезается первым) |
| `catalogue` Разбор статей | агент | да | поиск (свежесть: статьи из свежей ленты) |
| `cards` Карточки идей | агент | да | исследователь (свежесть: идеи из его записки), каталог (порядок трат) |
| `generate` Генератор идей | агент | да | каталог, руководитель (свежесть), карточки (порядок трат) |
| `second_venue` Вторая площадка для закрытых идей | код | нет | пересчёт (свежесть: выбирает по последнему исходу) |
| `ladder` Лестница оценки | код | нет | все, кто пишет прогоны (свежесть); чтение, токенов нет |

Что изменилось в самих этапах: этап аномалий разрезан на два шага (проверка кодом и разбор
агентом): так надстройки зависят только от проверки кодом, и выключить токены не значит выключить
надстройки. Остальное — те же функции, что и были, вызванные из таблицы.

## Как читать страницу

* **Цвета.** Зелёный — прошёл. Красный — упал (внутри шага текст ошибки). Синий — идёт сейчас.
  Жёлтый — заблокирован: шаг не запускался, потому что упал или выключен тот, чей результат ему
  нужен (в карточке шага написано, какой). Серый — выключен, сегодня не нужен по расписанию
  (исследователь, руководитель, генератор работают не каждую ночь) или ещё ждёт своей очереди.
  Оранжевый — прерван: процесс остановили (или он умер) посреди шага.
* **Дорожки.** Полосы по времени: на каждой дорожке (расчёты, проверки, агенты, итог) шаги стоят
  там, где шли, слева направо; идущие сейчас тянутся до «сейчас». Подпись говорит, во сколько раз
  сумма времён шагов больше стены: во столько дорожки сработали вместе. Шаг, ещё не начатый или
  выключенный, виден строкой под дорожкой. В карточке шага написано, на какой он дорожке и что из
  остального идёт вместе с ним на самом деле.
* **Дерево.** Колонка — «волна»: шаги одной волны ничем не связаны, они могли бы идти
  одновременно. Сплошная тёмная линия — связь «данные», остальные виды — пунктиром. Галочка
  «не держать порядок трат токенов» убирает связи «порядок трат» и перестраивает колонки:
  видно, что было бы без этой очерёдности. Утренний отчёт линиями не нарисован (он ждёт всех).
* **Шаг.** Нажмите: описание, от кого и от чего он зависит с причиной каждой связи, что может
  идти одновременно с ним, статистика (запусков, доля успешных, среднее и медиана, самый долгий,
  токены, последняя ошибка), из чего состоит последний запуск (имя, время, исход) и история
  запусков. «≈» — время восстановлено по отметкам прошлых ночей, не замерено: это нижняя
  оценка (от первой отметки до последней в пределах одного запуска). Строка истории раскрывается:
  в ней части именно того запуска, поэтому попытки одного дня (прерванная утренняя и вечерняя)
  видны каждая со своими частями.
* **«Что занимает время»** — таблица всех шагов по убыванию длительности в последней ночи,
  с долей, медианой и самым долгим запуском. Это и есть ответ на «что так долго идёт».
* **«Запуски»** — журнал запусков: кто запустил (расписание, кнопка, вручную), чем закончился,
  что выключено.

## Кнопки

**«Запустить весь пайплайн…»** — окно со списком шагов: снимите галочку с шагов, которые не
нужны. Тут же показано заранее: сколько шагов запустится, **какие тратят токены**, что выключено,
и какие шаги не запустятся, потому что зависят от выключенного (если тот сегодня не выполнялся).
«Выключить все шаги с токенами» — одним нажатием.

**«Перезапустить шаг…»** (в карточке шага) — перезапускает шаг **и всё, что берёт его
результат** («по данным»): их отметки «сделано» в состоянии ночи стираются, и они идут заново. К
ним всегда добавляются лестница и отчёт (они только читают). Шаги, которые лишь читают его
результат «по свежести», не перезапускаются, но окно называет их. Перед запуском окно называет
шаги, которые потратят токены; кнопка подтверждения тогда подписана «…и потратить токены».
Перезапуск агента: шаг вызывает агента заново, но его собственные ведомости (что уже
разобрано, сколько попыток) по-прежнему могут пропустить сделанное.

Правила обоих окон — одна функция (`qlab.nightflow.plan.make_plan`), которой пользуется и
сам запуск, поэтому то, что окно пообещало, и то, что запуск сделал, не расходятся.

**Одна ночь за раз.** Запуск берёт замок на `data/night/run.lock` (замок операционной системы:
он снимается сам, как бы ни кончился процесс). Тот же замок берёт ночь от launchd в 03:20 и
запуск вручную, поэтому кнопка не запустит вторую ночь поверх идущей, а причину отказа пишет:
«Уже идёт запуск (ночь по расписанию, с 03:20, процесс …)». Обратное тоже верно: если днём кто-то оставил запуск с кнопки идти до 03:20, ночь по
расписанию не стартует (`exit 75` и строка в `data/night/logs/<дата>.log`). Кнопка также не даст запустить
второй раз, пока первый ждёт рекордера (скрипт ночи ждёт, пока допишет `record-daily.sh`).

**Запуск живёт на своём процессе.** Кнопка запускает `ops/night.sh` в отдельной сессии:
процесс не умирает с консолью и с API, его журнал — `data/night/logs/<дата>.log`, как у ночи по
расписанию, внутри `caffeinate`. В журнале запуск записан как `button`. Если процесс убит
(SIGTERM, `kill`), запуск и шаг в журнале становятся «прерван»; если умер совсем без
предупреждения, их помечает «прерван» следующий запуск, а страница показывает это сразу (замок
свободен, а строка говорит «идёт»).

**Только на этой машине.** Консоль до сих пор только читала; это её единственное изменение, и
оно не меняет реестр: API лишь запускает процесс. Три запроса (`/api/pipeline/preview`, `/run`,
`/restart`) принимаются только с адреса 127.0.0.1, с заголовком консоли и с локальным именем
хоста; запрос с чужой страницы отклоняется. API слушает только 127.0.0.1.

## Команды

```bash
uv run qlab night steps                      # шаги, волны, связи
uv run qlab night run                        # вся ночь, дорожками (по умолчанию --concurrency 3)
uv run qlab night run --concurrency 1        # вся ночь по одному шагу, в порядке таблицы
QLAB_CONCURRENCY=1 ops/night.sh              # то же для ночи по расписанию, без правки кода
uv run qlab night run --off research --off generate    # выключить шаги
uv run qlab night run --restart recheck      # шаг и всё, что берёт его результат
uv run qlab night run --only paper --only decay        # только эти шаги
uv run qlab night backfill                   # приблизительная история из прошлых ночей
```

Старые флаги (`--no-research` и другие) работают, как работали: шаг пропускается, и никто
не блокируется. Блокирует только `--off` (и кнопка).

## Приблизительная история

По записям `data/night/*.json` и `data/night/logs/*.log` восстановлено 29 ночей (с 3 по 31
октября): какие шаги оставили следы, у шагов с отметками «сделано» — время от первой отметки
до последней в пределах одного запуска, из чего шаг состоял. Всё помечено «приблизительно»,
в статистику замеренных запусков не входит, шагам без следов времени не приписано. Времена —
нижняя оценка: первое дело шага начинается до его первой отметки.

## Можно ли запараллелить

Короткий ответ: **да, и теперь это сделано дорожками** (раздел «Дорожки» ниже). Выигрыш зависит
от ночи, а не от числа ядер: ночь не ускоряется, если она упирается в один шаг, который ждёт
площадку, зато остальные шаги больше не стоят за ним. Анализ ниже написан до того, как дорожки
появились; в нём объяснено, почему именно три дорожки, а не «все шаги сразу».

### Что показывает граф

Из связей выше (25 шагов, у 8 из них есть настоящие «данные»):

* У графа один настоящий корень — определители режима. Если убрать порядок трат токенов, корней
  становится шесть: определители и пять агентских шагов (программист, руководитель, исследователь,
  реализация, поиск), которых друг с другом связывает только очерёдность расхода.
* Цепочка агентов (второе мнение → программист → руководитель → исследователь → реализация →
  поиск → каталог → карточки → генератор) — это очерёдность расхода токенов, а не передача
  данных. Если её держать, агенты идут друг за другом; если нет — они независимы от кода и друг
  от друга.
* Настоящая цепочка данных короткая: определители → список → второе мнение; проверка кодом →
  надстройки; исследователь → двойники экспериментов; сверка бумаги → угасание → распределение.

руководителем, реализация с поиском и генератором — одной суммой на ночь 30 октября).

в это время, а не стоять за ним. Ночь 31 октября потому и осталась без агентов. Ночь 30 октября
упиралась в сумму многих шагов, и там параллельность даёт много: примерно треть-половина.

### Что ограничивает

1. **Лимиты площадок.** Hyperliquid отдаёт запрос в секунду, второй качающий получит 429 и
   минуту ожидания; Binance — 500 запросов на историю фандинга за 5 минут (сейчас два потока).
   Два шага, которые качают одну площадку, друг друга не ускорят. Это и есть 135 и 204 минуты
   выше: на этом пределе параллельность ничего не даёт. Блокировка на площадку в фоновой закачке
   (`qlab.prefetch`) уже есть и должна остаться общей.
2. **Запись в реестр (SQLite).** (Решено, см. «Дорожки».) Один пишущий; режим WAL и ожидание до минуты спасают от отказов,
   но два шага, пишущих испытания, будут ждать друг друга. Есть и скрытое место: нумерация
   версий спека у шумовых идей (поиск строки спека в `qlab.pipeline.evaluate`) предполагает, что
   одну идею за раз считает один шаг; `restamp` и `recheck` на одной идее дали бы дубли.
   Поэтому связи «не вместе».
3. **Общее состояние ночи.** (Решено: у каждого шага своя копия.) Все шаги пишут в один словарь `state` и сохраняют его целиком
   (`save_state`): при двух шагах сразу сохранение может упасть на «словарь изменился во время
   обхода». Нужно разделить состояние по шагам (у каждого свои ключи — они в таблице) и
   сохранять под замком. Метки «сделано» уже разнесены по префиксам шагов.
4. **Счёт делят ядра.** Случайные книги уже считаются в 10 процессах (на 16 ядрах), поэтому два
   счётных шага сразу не вдвое быстрее: выигрыш — там, где один шаг ждёт площадку или модель, а
   другой считает.
5. **Токены.** (Решено: агенты по одному на своей дорожке.) Гард бюджета (`qlab.budget`) считает расход шаг за шагом; два агента сразу могли
   бы потратить больше потолка до следующего замера. Цепочку агентов держать по одному — это и
   есть связи «порядок трат».
6. **Реализатор правит каталог исходников** (решено: см. «Дорожки», раздел про дерево файлов), пока идут другие шаги, которые подгружают модули.
   Реализацию лучше не запускать вместе с кодовыми шагами.

### Ожидаемая экономия и что делать дальше

* На ночи, похожей на 30 октября: **со 155 минут примерно до 95-100 при двух шагах сразу** (в
  таблице 95 — без учёта, что счётные шаги делят ядра), до 75 при трёх. Практически — одна
  дорожка кода и одна дорожка агентов, которые идут вместе, сверка бумаги в третьей.
* На ночах 29 и 31 октября: 12-27% (в таблице выше), и главное — агенты и надстройки успевают, пока медленный шаг
  качает. Ускорит их только меньшее число запросов (например, не качать заново фандинг,
  который уже лежит в кэше другого интервала, `docs/NIGHT_SPEED.md`).
* Порядок работ: (1) разделить состояние ночи по шагам и сохранять под замком;
  (2) включить две дорожки — агенты отдельно, код отдельно, без общих ключей состояния;
  (3) замерить на копии реестра и на живой ночи; (4) только потом повышать число шагов сразу.
  Параллельность агентов между собой и с реализатором не включать вовсе.
* Что принесёт больше любой параллельности: убрать то, что стоит самого долгого. 36 минут
  30 октября легли между сверкой бумаги и вторым мнением, и по отметкам нельзя сказать, угасание
  это или распределение: журнал теперь покажет это по шагам. 204 минуты 31 октября ушли на свечи;
  теперь их ограничивают `night/restamp.yaml` и `night/second_venue.yaml` (минуты за ночь).

## Дорожки (2026-10-31)

Владелец, 2026-10-31: «посмотри что нужно сделать чтобы запускать параллельно» ... «я имею ввиду
шаги пайплайна»; три дорожки одобрены. Две ночи пропали из-за того, что один долгий шаг занял
время всех шагов после него. Теперь шаги идут **дорожками**: на каждой дорожке шаги идут по одному,
дорожки идут вместе.

| Дорожка | Шаги (в порядке таблицы) | Почему по одному |
|---|---|---|
| **Расчёты** | определители → список наблюдения → ждущие идеи → двойники → пересчёт старых → почему площадки расходятся → аномалии (проверка кодом) → надстройки → двойники экспериментов → вторая площадка | Все пишут испытания идей через стенд и общие списки (`data/twins`, `data/restamp`, …). Одну идею два шага посчитали бы дважды, и дефляция учла бы оба раза. |
| **Проверки** | сверка бумаги → угасание → распределение | Читают боевой хост (только чтение) и кэш панелей стенда; испытаний не пишут. Одна цепочка: угасание берёт выгрузку сверки, распределение — результат угасания. |
| **Агенты** | второе мнение → разбор аномалий агентом → программист → руководитель → исследователь → реализация → поиск → каталог → карточки → генератор | Гард токенов не рассчитан на два вызова сразу: он читает окна, делит остаток и пишет расход вызов за вызовом. Порядок трат — тот же, что был (CLAUDE.md: дешёвое и обязательное первым, поиск нового режется первым). |
| **Итог** | лестница → отчёт | После всех остальных дорожек. |

**Двойники экспериментов** (шаг, который идёт после исследователя) — на дорожке расчётов, хотя
ждёт агента: это тот же код, тот же журнал двойников (`data/twins/ledger.json`) и тот же блок
состояния `twins`, что у шага «Двойники», и он пишет испытания идей. Он стоит в очереди
расчётов и стартует, когда исследователь закончил и дорожка свободна. Остальные шаги расчётов
ждут его не обязаны: дорожка берёт **первый готовый** шаг в порядке таблицы, поэтому шаг, который
ждёт другую дорожку, не задерживает тех, кто стоит за ним.

**Как выбирается шаг.** Шаг стартует, когда закончились все родители, чей результат он ждёт
(связи «данные», «свежесть» и «не вместе»), и его дорожка свободна. Связь «порядок трат» шаг **не
держит** (правило с 2026-11-01, ниже): дорожка берёт первый **готовый** шаг в порядке таблицы. Упавший шаг по-прежнему блокирует только тех, кто берёт его результат по
«данным», в любой дорожке; остальные идут. Связи между дорожками остаются настоящими:

* второе мнение ждёт список наблюдения (данные) и сверку бумаги (свежесть);
* сверка бумаги ждёт список наблюдения (свежесть): она сравнивает бумагу с проверкой вперёд на
  стенде; угасание тоже ждёт список наблюдения — оно читает кэш панелей стенда, который
  докачивается списком (проверено по коду: `run_decay` берёт только готовые снимки, не качает);
* разбор аномалий агентом ждёт проверку аномалий кодом (данные); программист, руководитель,
  исследователь, реализация, поиск, каталог, карточки и генератор разбора **не ждут** (см. «Очередь
  агентов не ждёт чужую дорожку»);
* двойники экспериментов ждут исследователя (данные);
* лестница и отчёт ждут всех.

### Очередь агентов не ждёт чужую дорожку (2026-11-01)

Первая ночь на трёх дорожках (запуск 31) показала ложную очередь. Разбор аномалий агентом ждёт
проверку аномалий кодом, а она стоит в конце дорожки расчётов, после ждущих идей (95 минут). Программист был
привязан к разбору связью «порядок трат», и дорожка агентов простояла **с 01:26 до 03:06 UTC —
99 минут**, хотя программист, руководитель и остальные могли работать с первой минуты. (Аудит на
журнале запуска 31: `python scripts/rehearse_lanes.py idle data/qlab.db agents`, он находит этот
простой и ещё 65 минут в начале ночи, когда программист стоял за вторым мнением.)

Правило планировщика теперь такое: **свободная дорожка берёт первый шаг в порядке таблицы, который
готов; шаг, чей настоящий родитель по данным ещё не закончился, пропускается.** «Порядок трат»
(`budget`) остаётся в таблице как пояснение очерёдности, но шаг не держит:
`GATING_KINDS = (data, fresh, exclusive)` в `qlab.nightflow.table`. Связь «разбор аномалий →
программист» убрана совсем. Что осталось: агенты по-прежнему **по одному**; исследователь → двойники
экспериментов (данные) на месте; разбор аномалий идёт, когда закончилась проверка, в ближайшем
свободном окне дорожки. Цена: программист, руководитель и исследователь теперь идут раньше
второго мнения (решение владельца 2026-10-30: токены сначала программисту); второе мнение идёт, как
только готов список наблюдения и сверка бумаги, в первое свободное окно.

Доказательство — репетиция настоящего `qlab night run` на копии проекта и копии реестра, все шаги
заглушки, длительности запуска 31 в масштабе 1 минута = 0,5 с, три дорожки (запуск 32 копии):

| шаг дорожки агентов | старт, с | конец, с |
|---|---|---|
| программист | 0,0 | 29,8 |
| руководитель | 29,8 | 32,4 |
| исследователь | 32,4 | 34,6 |
| второе мнение | 34,7 | 35,3 |
| реализация | 35,3 | 35,4 |
| поиск | 35,4 | 38,8 |
| каталог | 38,8 | 38,9 |

Дорожка агентов не стояла ни секунды, пока один из её шагов был готов (аудит `idle`:
«lane idle while a step was ready: never»). Второе мнение пошло в 34,7, а не в 32,4, потому что
ждало сверку бумаги (свежесть; закончилась в 32,8), а исследователь был готов раньше. Разбор

`test_the_agents_lane_is_never_idle_while_one_of_its_steps_is_ready`.

**Потоки, а не процессы.** Дорожки — это потоки одного процесса. Решающие доводы: журнал,
замок ночи, сигнал остановки, общий пул шумовых книг, один движок реестра и состояние ночи —
всё это живёт в одном процессе; тяжёлое (шумовые книги) и так считается в десяти отдельных
процессах, сверка бумаги запускает свои. Процесс на дорожку потребовал бы сводить состояние и
журнал между процессами и сильно рисковал бы там, где сейчас всё проверено. Цена потоков —
общий интерпретатор: счёт самих стратегий в основном потоке расчётов и проверок делит
интерпретатор (numpy и pandas отпускают его на больших операциях). Поэтому выигрыш по времени —
от ожидания (агенты, площадки, пул, ssh), а не от второго ядра под тот же расчёт.

### Состояние ночи: у каждого шага своя копия

Раньше все шаги писали в один словарь `state` и сохраняли его целиком. Теперь
(`qlab.nightflow.statehub`):

* в начале шага он получает **копию** состояния: чужие результаты он читает из неё (они записаны
  раньше, потому что связи таблицы заставили родителей закончить), свои пишет в неё, как писал
  в общий словарь;
* при каждом сохранении (`night.save_state`) хаб под замком переносит в общее состояние **только
  ключи этого шага** (`state_keys` в таблице) и его отметки «сделано» (префиксы `done_prefixes`)
  и атомарно пишет файл. Никто не обходит словарь, который меняет другой поток;
* два шага не могут владеть одним ключом, если таблица не ставит один из них после другого: это
  проверяется при загрузке таблицы. Поэтому ключ ждущих идей `waiting_followed` отделён от ключа
  `unwatched_bench` списка наблюдения, а «входящие идеи» руководителя (`ideas_in_director`) от
  исследовательских (`ideas_in`);
* шаг, изменивший чужой ключ, делает запись, которая потеряется: это считается нарушением
  (печатается в журнал запуска; с `QLAB_STATE_STRICT=1` — ошибкой шага). Тесты и репетиция идут в
  строгом режиме; в них нарушений нет;
* общие ключи (`stage_errors`, `stopped_at`, `deadline`, `prefetch`, `account`, `limits_off`)
  меняются только через хаб; возобновление по отметкам «сделано» работает как раньше: файл тот
  же, ключи те же.

**Кто чем владеет** (из `night/pipeline.yaml`; ключ с двумя владельцами — только там, где один шаг
всегда после другого):

### Реестр: короткие записи

В реестре (SQLite) один пишущий. Два шага, которые пишут, раньше ждали бы друг друга по минуте и
падали на «database is locked», если один держит блокировку долго. Что сделано:

* **`evaluate_spec`** отпускает блокировку записи (commit) сразу после строки спека и ещё раз
  после загрузки панели, до долгого счёта; испытание пишется коротко в конце. Раньше строка
  спека держала блокировку на всё время закачки свечей.
* **Вызов агента** (`run_agent`) записывает ожидающее до вызова и расход после него: вызов
  длится минуты, а блокировка раньше держалась всё это время.
* **Номера версий спека.** `_next_version` берёт максимум и прибавляет единицу — два пишущих по
  одной идее взяли бы один номер. Теперь чтение и вставка идут под замком идеи, вставка
  записывается до отпускания замка; запись другого процесса (ручная команда) ловится уникальным
  ключом (идея, версия) и номер читается заново. Строки спеков шумовых книг
  (`ensure_spec_rows`) нумеруются так же, под замками шумовых идей в одном порядке.
* **Журнал.** Каждый вызов журнала — своя короткая транзакция; вызовы идут по одному и, если
  реестр занят, повторяются (до четырёх раз). Это безопасно, потому что вызов — целая
  транзакция.
* **Взаимоблокировка 31 октября** (`_release_write_lock`: кандидат держал блокировку записи, пока
  ждал шумовые книги, а им нужно было записать испытания) остаётся исправленной: ни один шаг не
  ждёт воркеров с открытой записью, а долгие записи теперь видны — см. репетицию.
* **Пул шумовых книг** один на процесс: десять процессов при 16 ядрах, сколько бы дорожек ни
  просили книги (`QLAB_NOISE_WORKERS` меняет число; на машине с меньшим числом ядер его надо
  уменьшить). Очередь пула — общая очередь всех дорожек. Пул создаётся и останавливается под
  замком; упавший пул заменяет первый, кто заметил, остальные находят новый целым.
* **Кэши в памяти** (внутренний ход надстройки, переподгонка, эталонные веса шумовых книг, ход
  Bv2) — `qlab.boundedcache.BoundedCache` под замком: раньше они выбрасывали старое
  `pop(next(iter(...)))` и с двумя потоками падали.

### Гард токенов и агенты

Дорожка агентов идёт по одному шагу. `run_agent` проверяет, что вызов делает шаг дорожки агентов
(или поток вне ночи: консоль, ручная команда), и берёт замок: вызовы идут по одному. Ни один
шаг дорожек расчётов и проверок гард не вызывает (проверено: модули этих шагов не импортируют
`qlab.budget`; разбор аномалий кодом выходит до агентской части). Доля бюджета стадии
(`night_share`) считается от остатка ночи **в момент старта стадии** по свежему замеру окон; от
того, закончился ли шаг расчётов раньше или позже агента, она не зависит.

### Агенты и дерево файлов

Агенты, которые пишут файлы (реализатор, исследователь, каталог, карточки, руководитель, разведчик,
генератор), после вызова смотрят `git status` и откатывают всё, что не их. Пока дорожка расчётов
пишет рядом спеки (двойник `-causal.yaml`, вариант надстройки, спек второй ступени), такая проверка
приняла бы их за чужие и удалила. Функции записи сообщают об этом (`qlab.tree_writes`), и проверки
агентов эти файлы не трогают.

Реализатор и исследователь **пишут испытания** (запуск на стенде) на дорожке агентов, рядом с
дорожкой расчётов. На одну идею они сходятся только через строку спека (идея, версия) — это
закрыто замком идеи и повтором; решение «какие идеи считать сегодня» остаётся у дорожки расчётов
(пересчёт и вторая площадка берут идеи по последнему исходу, а новые идеи агентов они в эту же
ночь не видели и раньше).

### Что остаётся по одному и почему

* на дорожке расчётов — всё: общие списки, одни и те же идеи, строки спеков шумовых идей;
* на дорожке агентов — всё: гард токенов;
* закачка с одной площадки — по одной в процессе (`qlab.data.snapshot._venue_lock`: пауза между
  запросами рассчитана на один процесс; Hyperliquid — один запрос в секунду, Binance — 500
  запросов истории фандинга за 5 минут). Если дорожка расчётов качает с площадки, агент, которому
  нужны те же свечи, ждёт: это и было причиной 135 и 204 минут;
* закачка одного и того же запроса — один раз (`_request_lock`), кто пришёл вторым, берёт готовое.

### Включение и откат

`qlab night run --concurrency 3` — дорожки; `--concurrency 1` — порядок таблицы, как было.
`QLAB_CONCURRENCY=1 ops/night.sh` откатывает ночь по расписанию без правки кода. Страница
показывает дорожки полосами по времени и подпись «сумма времён шагов / стена».

## Лимит времени на шаг (2026-11-01)

Владелец, 2026-11-01 («да, делай по порядку»), после первой ночи на трёх дорожках. Ждущие идеи
шли **94,7 минуты, из них 72,5 — вторая ступень одной идеи** (книга Bv2 на 38 контрактах, около 800
сборок рынка по ~6 с в журнале); оценка и лимит времени стояли только у «пересчёта старых» и «второй
площадки». Теперь тот же страж (`qlab.stage_time`) стоит на каждом шаге дорожки расчётов, который
гонит идеи через стенд из списка:

| шаг | лимит на ночь, мин | где задан |
|---|---:|---|
| ждущие идеи | 45 | `night/waiting.yaml` |
| двойники; двойники экспериментов (каждый шаг отдельно) | 30 | `night/twins.yaml` |
| надстройки | 40 | `night/overlays.yaml` |
| пересчёт старых; вторая площадка | 60; 30 | как было |
| список наблюдения | 60 (только отчёт) | `night/watchlist.yaml` |

* **Оценка до старта идеи.** Для ждущих идей это большее из объёма докачки (`qlab.hl_fetch`) и
  времени, которое идея заняла в прошлый раз (`data/stage_seconds.json`, пишет каждый запуск, в том
  числе ручной). Для двойников и надстроек — время прошлого раза.
* **Идея тяжелее всего лимита** — ночью не запускается; в отчёте и на странице стоит «слишком
  тяжело для ночи» и команда: `qlab twins run --only ИДЕЯ` (для надстроек `qlab overlays run
  --only БАЗА`). Ручной запуск лимита не имеет, и после него ночь знает, что идея стала быстрой.
* **Идея больше остатка** — ждёт следующей ночи. **Время вышло** — новое не начинается.
* **Сторожок перерасхода.** Идея, которая вывела шаг за лимит, не обрывается (испытания записаны);
  отчёт и страница называют её, а ночь не возьмёт её снова, пока ручной запуск не покажет, что
  она ускорилась.
* **Список наблюдения не пропускается никогда**: это список владельца, он идёт каждую ночь, чего
  бы ни стоил. Шаг только записывает время каждой стратегии и **сообщает**: ночь, в которую список
  занял больше лимита, и каждая стратегия, занявшая больше `slow_item_minutes` (15). В запуске 31 это
  46,6 минуты и одна стратегия на 17,2.
* Ключи состояния: `waiting_time`, `recheck_time`, блок `time` в `twins` и `overlays`. Страница
  показывает это в строке шага.

### Почему рынок собирался заново около 800 раз

Спек второй ступени `bv2-research-top10-pool-hl` называет `kNEIRO` — так монета пишется на
Hyperliquid (тысячекратные контракты `kNEIRO`, `kPEPE`, `kBONK`), а в манифесте снимка она записана
так же. Поиск готового снимка (`_find_matching_snapshot`) приводил к верхнему регистру только
**запрос**, не манифест: `KNEIRO` ≠ `kNEIRO`, снимок «не находился», и **каждый запуск спека,
в том числе каждая из 200 шумовых книг и каждая замена, собирал рынок заново** (≈ 100 с в одном
процессе, около 54 с на замере; 400 книг с ошибкой «Bv2 needs column BNB-SPOT» по 10 в параллели —
вот эти 72 минуты). Поправлено: оба названия сравниваются в верхнем регистре, как и строит снимок
`_resolve_casing`. Оценка докачки (`hl_fetch`) тоже читала «снимка нет» и считала подвоз.

Доказательство на копии реестра: снимок, собранный заново, и найденный на диске — один и тот же
(`6e1a80c31713…`, идентификатор считается по содержимому); цены, ставки, маска торгуемости и
объёмы совпадают до значения (индекс времени отличается только единицей: миллисекунды против секунд);
стратегия «равные доли пяти контрактов» на тех же данных дала **одни и те же 95 метрик, тот же
маршрут и ту же причину** при поиске снимка (0,2 с) и при пересборке (53,6 с); три шумовые книги
этого спека дали одинаковый результат в обоих режимах (ошибка того же текста: у этой книги на
Hyperliquid нет `BNB-SPOT`, Bv2 на этой панели не считается — это отдельный вопрос).

## Части запуска и попытки одного дня (2026-10-31)

Файл состояния ночи (`data/night/<дата>.json`) хранит весь день: если ночь запущена второй раз
(кнопкой после прерванной), этап находит в нём записи утренней попытки рядом со своими. В запуске
30 из-за этого шаг «пересчёт» показывал сбой утренней попытки (`frab-binance-spot-allbinance-400`,
«database is locked») и строку с именем «?», а счётчики частей были 1/2 и 4/3, хотя в этом запуске
не упало ничего.

Теперь так:

* В момент старта шага журнал запоминает, какие сбои в состоянии уже есть. Частями запуска
  считаются только сбои, появившиеся после старта (сравнение по паре «имя, текст» с учётом числа
  повторов: тот же сбой, случившийся ещё раз в этом запуске, считается). Сделанные части и раньше
  брались только из новых отметок «сделано».
* Строка без имени не появляется: сбой внутри записи идеи называется по идее, а сбой без имени
  вообще — по ключу состояния (`restamp`). Вложенный сбой той же записи не считается второй раз.
* Утренний отчёт называет идею один раз — по её последней записи. Запись, сделанная раньше
  последнего запуска этапа, помечена «прошлый запуск этапа этой ночью, ЧЧ:ММ UTC». Время этапа в
  разделе «вторая площадка» подписано как время последнего запуска.
* Запись получает метку `at`, этап — `attempt_at` (`src/qlab/attempts.py`).
* Страница: части шага — только своего запуска, а прошлые попытки дня открываются строкой истории
  (`/api/pipeline/step-runs/<номер>/items`).

Журнал запуска 30 поправлен вручную: сбои утренней попытки перенесены к шагам запуска 29, а у
запуска 30 счётчики пересчитаны.

## Что осталось и о чём помнить

* Число шагов сразу задаёт `--concurrency`: 1 — порядок таблицы, 3 — дорожки (раздел «Дорожки»).
* Токены шага считаются по интервалу его работы (`token_spend` между началом и концом). Шаги с
  токенами лежат на одной дорожке и идут по одному, поэтому их интервалы не пересекаются друг с
  другом; шаги расчётов токенов не тратят.
* Шаг, проглотивший собственный сбой в состоянии ночи (угасание, распределение, сверка
  бумаги), в журнале помечен упавшим по тексту, который он сам записал. Шаги, которые внутри себя
  собирают отчёт об ошибках по пунктам (список наблюдения, ждущие идеи), остаются зелёными, а
  пункты с ошибкой видны красным внутри шага и числом на карточке.
* Старые запуски до 31 октября в журнале приблизительные; настоящие появятся с первой ночи
  после включения.
